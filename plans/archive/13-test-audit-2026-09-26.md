## High-impact findings (1–6)

### 1. Happy-path fixture contradicts shared changelog — `tests/test_issue_branch:597-607`, fixture `tests/test_issue_branch:162-184`

- New success case releases `v1.3.0` and expects a new dated `1.3.0` heading.
- Shared fixture already contains a previous `1.3.0` heading, so the test would bless
  duplicate `1.3.0` headings.
- Fix (essential): make the happy-path candidate newer than the fixture history (e.g. `1.4.0`)
  and assert exactly one heading for the released version.
- Optional additional release-integrity assertion: check the tag dereferences
  to `HEAD` / the committed changelog.

### 2. New negative guards miss the actual faulty release — G1 `tests/test_issue_branch:642-651`, G2 `tests/test_issue_branch:655-661`

- G1 asserts absence of `v1.4.0`, but the faulty `src/issue-branch` patch default
  produces `1.4.1`; absence passes even after the wrong tag is created.
- G2 only counts existing `1.3.0` headings while the faulty source promotes `1.3.1`,
  so the count passes while the wrong release happens.
- Status assertions still correctly fail today; these tests are not already fully green.
- Both could turn green for an unrelated `exit 1` / after-side-effect reason.
- Fix (essential): assert clean successful setup, keep the exit-status checks, then
  snapshot/compare pre/post `HEAD`, version, changelog, and ALL tag names (checking
  only `v1.4.0` misses the observed `v1.4.1`).
- Optional additional confidence: check the specific rejection diagnostic.

### 3. No-push test cannot detect pushes — `tests/test_issue_branch:668-675`

- No remote configured, does not check `create`/`finish` exit status, never invokes `release`.
- Fix: use a local Git wrapper recording push invocations or a local bare remote, call
  both commands, assert success and zero push calls.

### 4. Non-portable, silent-pipeline blob comparison — `tests/test_issue_branch:476-484`

- `git show | sha256sum` twice: `sha256sum` is unavailable on stock macOS/POSIX, and
  without `pipefail` / `set -e` two empty results compare equal.
- Fix: compare verified Git blob IDs via `git rev-parse --verify` with independent status checks.

### 5. Status mutation check misses worktree — `tests/test_issue_branch:397-420`

- Compares `HEAD:CHANGELOG.md` before/after only; misses uncommitted working-tree changes.
- Fix: snapshot the worktree file and `git status --porcelain`.

### 6. Empty-Unreleased rejection misses pre-rejection mutation — `tests/test_issue_branch:625-632`, source `src/issue-branch:556-569`

- Asserts only `exit 1`; source writes the bump before the changelog rejection, so the
  test passes despite a mutated version.
- Fix: assert before/after version, changelog, `HEAD`, and tag state.

## Moderate-impact findings (7–9)

### 7. Create-template test checks CLI output, not commit — `tests/test_issue_branch:269-278`

- Checks CLI `status` output, not the committed dev version.
- Fix: assert `HEAD:sample/__about__.py` and a clean worktree.

### 8. Hard-coded year literals — `tests/test_issue_branch:435`, `tests/test_issue_branch:533`

- `'2026-'` literals fail in Jan 2027.
- Fix: dynamic date or structural unique-heading assertion.

### 9. Setup helpers are not fail-fast — e.g. `tests/test_issue_branch:294-299`, `tests/test_issue_branch:234`

- Unchecked initial `create` in the duplicate-branch case is the main risk: if both
  creates fail for the same reason, the `status1` test falsely passes.
- Less-likely but real fixture-safety edge case: unchecked `mktemp` failure leaves
  `WORK` empty, which can create an absolute `/create` path; check `mktemp` status.
- Fix: explicit setup/`mktemp` status checks; no global `set -e` since expected nonzero CLI
  statuses are captured.
